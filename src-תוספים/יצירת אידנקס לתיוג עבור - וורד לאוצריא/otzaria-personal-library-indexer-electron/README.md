זו הגרסה הגרפית (Electron, אפליקציית שולחן עבודה) של כלי אינדוקס הספרייה האישית לאוצריא. היא עושה בדיוק את מה שהכלי המקורי בשורת הפקודה עושה - סורקת תיקייה עם קבצי Word ו-PDF, דואגת שלכל כותרת Word תהיה סימנייה (bookmark) אמיתית, בונה מסמך-מלווה עם תוכן עניינים לכל PDF שיש לו outline, וכותבת קובץ מיפוי אחד personal-library-index.json - אבל דרך חלון גרפי בעברית במקום הקלדת תשובות בטרמינל.

כדי להריץ אותה: נכנסים לתיקיית הכלי, מריצים npm install (פעם אחת, מוריד את כל הספריות כולל את Electron עצמו), ואז npm start פותח את חלון האפליקציה. בחלון לוחצים "בחר תיקייה..." שפותח את דיאלוג בחירת התיקייה האמיתי של Windows. לצד זה יש שדה טקסט "תיקיית פלט" (ברירת מחדל: `_אינדקס_אישי`), שאפשר לערוך אם רוצים שם אחר לתיקיית התוצרים. אחר כך לוחצים "התחל סריקה". במהלך הסריקה מופיע יומן חי שמראה איזה קובץ מעובד כרגע ומה נמצא בו. אם הכלי נתקל בקובץ Word עם כותרות בלי סימנייה, נפתח חלון קטן ששואל מה לעשות - להוסיף למקור, להעתיק לקובץ חדש, או לדלג - בדיוק כמו השאלה מ/ה/ד בגרסת שורת הפקודה, רק בכפתורים. בסוף הסריקה מופיע מסך סיכום עם מספרי הספרים והכותרות שנמצאו, וכפתור שפותח את סייר הקבצים בתיקייה שבה נשמר קובץ המיפוי.

כל התוצרים שהכלי יוצר - המסמכים-המלווים ל-PDF (docx), קבצי ה-links.json שלהם, וקובץ המיפוי personal-library-index.json - נשמרים כיום בתוך תיקיית פלט אחת ויחידה שנוצרת בשורש התיקייה שנבחרה לסריקה (לא בתוך כל תת-תיקייה שבה נמצאים הספרים עצמם), כדי לא לפזר קבצים חדשים לתוך תיקיות הספרים המקוריות. שם ברירת המחדל של תיקיית הפלט הוא `_אינדקס_אישי`, וניתן לשנות אותו בשדה "תיקיית פלט" שבמסך הראשי. לדוגמה: אם התיקייה הנסרקת היא `books` וקובץ ה-PDF נמצא ב-`books\נושא\ספר.pdf`, המסמך-המלווה שלו ייכתב אל `books\_אינדקס_אישי\ספר - אינדקס.docx` (ולא לתוך `books\נושא\_אינדקס_אישי\...`). מכיוון שכעת כמה תת-תיקיות מקור חולקות תיקיית פלט שטוחה אחת, ייתכן ששני קבצי PDF בשם בסיס זהה בתת-תיקיות שונות (למשל `נושא1\ספר.pdf` ו-`נושא2\ספר.pdf`) היו מייצרים אותו שם קובץ פלט - ולכן כאשר ה-PDF אינו נמצא ישירות בשורש הנסרק, שם קובץ המסמך-המלווה (וגם קובץ ה-links.json שלו) מקבל קידומת של הנתיב היחסי של ה-PDF ביחס לשורש, עם "_" במקום מפרידי תיקיות - כך ש-`נושא1\ספר.pdf` הופך ל-`נושא1_ספר - אינדקס.docx` ו-`נושא2\ספר.pdf` הופך ל-`נושא2_ספר - אינדקס.docx`. קובץ שדה `sourcePath`/`pdfPath` שנכתב בתוך personal-library-index.json ממשיך להצביע על מיקומו האמיתי המקורי של כל קובץ - רק מיקום הקבצים הנוצרים עצמם זז לתוך תיקיית הפלט.

מבחינת מבנה: src/core מכיל את לוגיקת הליבה, שהועתקה מהכלי המקורי (src-תוספים/otzaria-personal-library-indexer) והותאמה כך שבמקום לשאול שאלות ישירות בטרמינל (readline) היא מקבלת פונקציית callback שמחזירה הבטחה (Promise) - כשיש כותרות בלי סימנייה, ה-scan עוצר וממתין (await) עד שההבטחה הזו תתמלא. src/main.ts הוא תהליך ה-Electron הראשי: הוא זה שפותח את דיאלוג בחירת התיקייה האמיתי (dialog.showOpenDialog), מריץ את הסריקה, ומעביר כל אירוע התקדמות לחלון דרך IPC (webContents.send). כשהסריקה צריכה החלטה על סימניות חסרות, ה-main יוצר מזהה בקשה ייחודי (requestId), שולח אותו לחלון יחד עם שם הקובץ, וממתין שהחלון יחזיר תשובה עם אותו מזהה בדיוק - כך שגם אם כמה קבצים ברצף דורשים החלטה, אף פעם לא תיתכן ערבוב תשובה בין קובץ אחד למשנהו. src/preload.ts חושף לחלון (לרנדרר) רק שורת פונקציות מפורשת וצרה (contextBridge), בלי לפתוח גישה כללית ל-Node או ל-Electron מתוך דף האינטרנט של הממשק - כפי שמומלץ לעשות מבחינת אבטחה. renderer/ מכיל את דף הממשק עצמו (HTML/CSS/JS רגילים, בעברית וב-RTL).

הרצת npm run test-core מריצה בדיקה עצמאית של שכבת הליבה בלבד (בלי לפתוח שום חלון Electron): היא יוצרת קבצי דוגמה (fixtures) עם docx ו-PDF - כולל שני קבצי PDF בשם בסיס זהה ("sample.pdf") בשתי תת-תיקיות שונות (שורש ו-sub), כדי לבדוק את מנגנון מניעת ההתנגשות בשמות קובצי הפלט - ומריצה עליהם את אותה פונקציית סריקה בדיוק כפי שה-main process של Electron מפעיל אותה, עם תשובות שונות לכל אחת מכמה בקשות סימניות-חסרות ברצף - כדי לוודא שהמנגנון "עוצר ומחכה לתשובה" עובד נכון גם כשיש יותר מקובץ אחד שדורש החלטה. הבדיקה גם מוודאת שכל התוצרים (מסמכים-מלווים, links.json, וקובץ האינדקס) נחתים בתוך תיקיית הפלט `_אינדקס_אישי` בשורש התיקייה הנסרקת, ושקידומת מניעת ההתנגשות פועלת נכון על שני קבצי ה-sample.pdf.

הערה סביבתית: בסביבת פיתוח שנמצאת מאחורי מסנן NetFree, הורדת קובץ ה-Electron עצמו בזמן npm install עלולה להיכשל עם שגיאת TLS/certificate או ECONNRESET. הפתרון: לייצא את שורש ה-CA של NetFree משורש האישורים של Windows לקובץ PEM (ראו את השיטה בזיכרון netfree_pip_and_zim_creation), להצביע עליו עם משתנה הסביבה NODE_EXTRA_CA_CERTS, ולהוסיף גם ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ כדי להוריד את הבינארי של Electron ממראה חלופית שאינה חסומה.
